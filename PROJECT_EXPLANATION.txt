  2. main.ts — BOOTSTRAP-UL APLICATIEI
================================================================================

async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  app.enableCors({ origin: 'http://localhost:3001' });
  → Permite cereri HTTP de pe frontend (localhost:3001).
    Fara CORS, browserul ar bloca raspunsurile de la backend (localhost:3000).

  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
  → ValidationPipe ruleaza automat validarile definite cu decoratori din
    class-validator pe toate DTO-urile.
    "whitelist: true" elimina automat orice camp din request care nu e definit
    in DTO (protectie impotriva campurilor neautorizate / mass assignment).
    "transform: true" activeaza class-transformer, permitand @Transform si
    conversia automata a tipurilor (ex: string -> number).

  app.useGlobalInterceptors(new ClassSerializerInterceptor(app.get(Reflector)));
  → ClassSerializerInterceptor aplica decoratorii din class-transformer
    (@Exclude, @Expose) pe toate raspunsurile API. Aceasta este mecanismul
    prin care campul "password" din entitatea User este exclus automat din
    toate raspunsurile, inclusiv din obiecte nested (ex: createdBy in PO).

  app.useGlobalPipes + app.useGlobalInterceptors = aplicate GLOBAL, nu trebuie
  repetate pe fiecare controller sau ruta.
}

  4. AUTENTIFICARE — JWT FLOW COMPLET
================================================================================

--- 4.1 Ce este JWT ---

JWT (JSON Web Token) este un token semnat criptografic care contine informatii
despre utilizator (payload). Serverul il semneaza cu un secret cunoscut doar
de el. La fiecare cerere, clientul trimite tokenul in header-ul Authorization.
Serverul verifica semnatura si extrage informatiile fara sa faca query la DB.

Format: <header_base64>.<payload_base64>.<signature>

Payload-ul nostru contine: { sub: userId, email, role }

--- 4.2 auth/dto/register.dto.ts si login.dto.ts ---

DTO = Data Transfer Object. Defineste forma si regulile de validare pentru
datele primite de la client.

class RegisterDto {
  @IsString() @IsNotEmpty()
  name: string;

  @IsEmail()
  email: string;

  @IsString() @MinLength(6)
  password: string;
  → Parola trebuie sa aiba minim 6 caractere. Validarea e facuta de
    ValidationPipe global, inainte ca request-ul sa ajunga in controller.
}

class LoginDto {
  @IsEmail()    email: string;
  @IsNotEmpty() password: string;
}

Daca validarea esueaza, ValidationPipe returneaza automat HTTP 400 cu
detaliile erorii, fara ca logica din controller sa fie atinsa.

--- 4.3 auth/auth.service.ts ---

register(dto: RegisterDto):
  1. Cauta in DB un utilizator cu acelasi email. Daca exista, arunca
     ConflictException (HTTP 409).
  2. Hash-uieste parola cu bcrypt (salt rounds = 10).
     bcrypt.hash(password, 10) — algoritmul bcrypt genereaza un salt aleator
     si aplica 2^10 = 1024 iteratii de hashing. Rezultatul include saltul
     incorporat, deci fiecare hash e unic chiar pentru aceeasi parola.
  3. Salveaza utilizatorul cu parola hash-uita (NICIODATA plaintext).
  4. Returneaza un mesaj de confirmare (nu tokenul — userul trebuie sa faca
     login separat).

login(dto: LoginDto):
  1. Cauta utilizatorul dupa email.
  2. Daca nu exista sau parola nu e corecta, arunca UnauthorizedException
     cu un mesaj generic ("Invalid credentials") — intentionat vag, ca sa nu
     dezvaluie daca emailul exista sau nu in sistem.
  3. Compara parola primita cu hash-ul din DB folosind bcrypt.compare().
     bcrypt.compare re-hash-uieste parola cu saltul din hash-ul stocat si
     compara rezultatele — nu stocam parola originala nicaieri.
  4. Semneaza un JWT cu { sub: user.id, email, role } si expirate de 1 zi.
  5. Returneaza { access_token: "..." }.

--- 4.4 auth/auth.module.ts ---

JwtModule.registerAsync({
  useFactory: (config) => ({
    secret: config.get('JWT_SECRET'),
    → Secretul vine din .env, nu e hardcodat in cod.
    signOptions: { expiresIn: '1d' },
    → Tokenul expira in 24 ore. Dupa expirare, clientul trebuie sa se
      autentifice din nou.
  }),
})

PassportModule — framework de autentificare care integreaza strategii
(local, jwt, oauth etc.) cu NestJS prin Guard-uri.

--- 4.5 auth/jwt.strategy.ts — STRATEGIA JWT ---

export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      → Extrage tokenul din header-ul "Authorization: Bearer <token>".
      ignoreExpiration: false,
      → Tokenul expirat este RESPINS automat.
      secretOrKey: config.get('JWT_SECRET'),
      → Acelasi secret folosit la semnare — verifica autenticitatea tokenului.
    });
  }

  validate(payload: { sub: string; email: string; role: string }) {
    return { id: payload.sub, email: payload.email, role: payload.role };
    → Aceasta metoda este apelata automat dupa ce Passport verifica semnatura
      JWT. Ce returneaza ea devine "request.user" in orice handler protejat.
      Nu facem query la DB aici — informatiile sunt deja in token.
  }
}

Flux complet al unei cereri autentificate:
  Client trimite "Authorization: Bearer eyJ..."
  → JwtAuthGuard intercepteaza cererea
  → Passport extrage tokenul din header
  → Verifica semnatura cu JWT_SECRET
  → Verifica ca tokenul nu e expirat
  → Apeleaza JwtStrategy.validate(payload)
  → Pune rezultatul in request.user
  → Controller-ul primeste cererea cu user-ul disponibil

--- 4.6 auth/jwt-auth.guard.ts ---

export class JwtAuthGuard extends AuthGuard('jwt') { }

Un Guard simplu care extinde AuthGuard din Passport cu strategia 'jwt'.
Aplicat pe un controller sau pe o metoda cu @UseGuards(JwtAuthGuard),
blocheaza orice cerere fara un JWT valid (HTTP 401).

================================================================================
  5. AUTORIZARE — ROLURI SI GUARD-URI
================================================================================

Autentificarea raspunde la "Cine esti?".
Autorizarea raspunde la "Ce ai voie sa faci?".

--- 5.1 auth/roles.decorator.ts ---

export const Roles = (...roles: UserRole[]) => SetMetadata('roles', roles);

Un decorator custom creat cu SetMetadata. Stocheaza lista de roluri permise
in metadata-ul handler-ului, sub cheia 'roles'. Folosit ca:

  @Roles(UserRole.ADMIN)
  @Get()
  findAll() { ... }

Decoratorul nu face nimic singur — e doar metadata. RolesGuard o citeste.

--- 5.2 auth/roles.guards.ts ---

export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) { }
  → Reflector e un utilitar NestJS care permite citirea metadata-ului
    stocat de decoratori (precum @Roles).

  canActivate(context: ExecutionContext): boolean {
    const requiredRoles = this.reflector.get<UserRole[]>('roles', context.getHandler());
    → Citeste lista de roluri necesare de pe handler-ul curent.

    if (!requiredRoles) return true;
    → Daca @Roles nu e aplicat pe ruta, oricine poate accesa (dar tot trebuie
      JWT valid din cauza JwtAuthGuard).

    const { user } = context.switchToHttp().getRequest();
    return requiredRoles.includes(user.role);
    → Compara rolul utilizatorului din request.user cu rolurile permise.
      Daca nu e inclus, canActivate returneaza false si NestJS trimite 403.
  }
}

Utilizare combinata:
  @UseGuards(JwtAuthGuard, RolesGuard) — pe controller = toate rutele protejate
  @Roles(UserRole.ADMIN) — pe o ruta specifica = doar ADMIN

--- 5.3 auth/current-user.decorator.ts ---

export const CurrentUser = createParamDecorator(
  (data: unknown, ctx: ExecutionContext): User => {
    return ctx.switchToHttp().getRequest().user;
  }
);

Decorator de parametru care extrage request.user (pus de JwtStrategy) si il
injecteaza direct in parametrul metodei din controller. Evita necesitatea de
a accesa manual request-ul.

Folosit ca:
  approve(@Param('id') id: string, @CurrentUser() user: User) { ... }

================================================================================
  6. ENTITATI SI MAPAREA LA BAZA DE DATE (TypeORM)
================================================================================

TypeORM este un ORM (Object-Relational Mapper) care mapeaza clasele TypeScript
la tabele PostgreSQL. Decoratorii definesc structura tabelei.

--- 6.1 users/user.entity.ts ---

@Entity('users')          → Mapeaza clasa la tabela "users" din PostgreSQL.
export class User {
  @PrimaryGeneratedColumn('uuid')
  id: string;
  → Cheie primara generata automat ca UUID (ex: "a1b2c3-...").
    Mai sigur decat auto-increment integer (nu se pot ghici id-uri).

  @Column({ unique: true })
  email: string;
  → Constrangere UNIQUE la nivel de DB — nu pot exista doua emailuri identice.

  @Exclude()              → Din class-transformer. ClassSerializerInterceptor
  @Column()               excludes acest camp din orice raspuns JSON.
  password: string;
  → Hash bcrypt stocat. Niciodata parola in plaintext.

  @Column({ type: 'enum', enum: UserRole, default: UserRole.REQUESTER })
  role: UserRole;
  → Coloana de tip ENUM in PostgreSQL. Valori permise: REQUESTER, MANAGER,
    IT, FINANCE, ADMIN. Default la inregistrare: REQUESTER.

  @CreateDateColumn()
  createdAt: Date;
  → TypeORM seteaza automat data curenta la INSERT. Nu trebuie setat manual.
}

--- 6.2 purchase-orders/purchase-order.entity.ts ---

@Entity('purchase_orders')
export class PurchaseOrder {
  @PrimaryGeneratedColumn('uuid') id: string;

  @Column() title: string;
  @Column({ nullable: true }) description?: string;

  @Column('decimal', { precision: 10, scale: 2 })
  amount: number;
  → Stocat ca DECIMAL(10, 2) in PostgreSQL — evita erorile de floating point
    (ex: 0.1 + 0.2 = 0.30000000000000004 in IEEE 754).
    precision: 10 = maxim 10 cifre total, scale: 2 = maxim 2 zecimale.

  @Column({ type: 'enum', enum: POCategory })
  category: POCategory;   → SERVICES | OFFICE_SUPPLIES | IT_EQUIPMENT

  @Column({ type: 'enum', enum: POStatus, default: POStatus.PENDING_MANAGER })
  status: POStatus;
  → Statusul curent in workflow. Posibile valori:
    PENDING_MANAGER → PENDING_IT → PENDING_FINANCE → INVOICED
                                ↘ NEEDS_REWORK (la reject)
                                ↘ PERMANENTLY_REJECTED (hard reject Finance)

  @ManyToOne(() => User)
  createdBy: User;
  → Relatie Many-to-One: mai multe PO-uri pot fi create de acelasi User.
    TypeORM creaza automat o coloana "createdById" (foreign key) in tabela.
    "() => User" este o referinta lazy la entitate, evitand circular imports.

  @CreateDateColumn() createdAt: Date;
  @UpdateDateColumn() updatedAt: Date;
  → updatedAt e actualizat automat de TypeORM la orice UPDATE.
}

--- 6.3 po-history/po-history.entity.ts ---

@Entity('po_history')
export class POHistory {
  @PrimaryGeneratedColumn('uuid') id: string;

  @ManyToOne(() => PurchaseOrder)
  purchaseOrder: PurchaseOrder;
  → FK catre purchase_orders. Fiecare intrare de history apartine unui PO.

  @Column({ type: 'enum', enum: POAction })
  action: POAction;
  → Actiunea efectuata: SUBMITTED | APPROVED | REJECTED | HARD_REJECTED |
    REWORKED | INVOICED

  @Column({ type: 'enum', enum: POStatus }) fromStatus: POStatus;
  @Column({ type: 'enum', enum: POStatus }) toStatus: POStatus;
  → Tranzitia de status. Ex: fromStatus=PENDING_MANAGER, toStatus=PENDING_IT
    reprezinta o aprobare de manager.

  @Column({ nullable: true }) comment?: string;
  → Comentariul la respingere (obligatoriu la reject, optional la altele).

  @ManyToOne(() => User)
  performedBy: User;
  → Cine a efectuat actiunea (manager, IT, finance etc.)

  @CreateDateColumn() timestamp: Date;
  → Data exacta a actiunii — baza pentru afisarea cronologica.
}

================================================================================
  7. DTO-URI — VALIDAREA DATELOR DE INTRARE
================================================================================

DTO-urile sunt clase TypeScript cu decoratori din "class-validator" si
"class-transformer". ValidationPipe (configurat global in main.ts) le
instantiaza automat si ruleaza validarile.

--- 7.1 purchase-orders/dto/create-po.dto.ts ---

class CreatePoDto {
  @Transform(({ value }) => value.trim())
  → class-transformer: trimite spatiile de la capete inainte de validare.
    Ex: "  Office chairs  " devine "Office chairs".

  @IsString() @IsNotEmpty() @MaxLength(200)
  title: string;
  → Trebuie sa fie string, nevid (inclusiv dupa trim), maxim 200 caractere.

  @Transform(...trim) @IsString() @IsOptional() @MaxLength(1000)
  description?: string;
  → Optional. Daca e trimis, maxim 1000 caractere.

  @IsNumber({ maxDecimalPlaces: 2 }) @IsPositive()
  amount: number;
  → Trebuie sa fie numar pozitiv cu maxim 2 zecimale.
    @IsPositive() respinge 0 si numerele negative.
    maxDecimalPlaces: 2 respinge 1.999 dar accepta 1.99.

  @IsEnum(POCategory)
  category: POCategory;
  → Accepta doar valorile din enum: 'SERVICES', 'OFFICE_SUPPLIES',
    'IT_EQUIPMENT'. Orice alta valoare e respinsa cu 400.
}

--- 7.2 purchase-orders/dto/uptdate-po.dto.ts ---

Identic cu CreatePoDto dar toate campurile sunt @IsOptional().
Are o validare speciala:

  @ValidateIf((o) => !o.title && !o.description && !o.amount && !o.category)
  @IsString({ message: 'At least one field must be provided' })
  _atLeastOne?: never;
  → Daca niciun camp nu e trimis, validarea esueaza cu un mesaj clar.
    "never" inseamna ca campul nu poate exista efectiv — e doar un
    hook pentru a declansa validarea.

--- 7.3 purchase-orders/dto/reject-po.dto.ts ---

class RejectPoDto {
  @Transform(...trim) @IsString() @IsNotEmpty() @MaxLength(1000)
  comment: string;
  → Motivul respingerii. Obligatoriu, nevid dupa trim, maxim 1000 caractere.
    Fara aceasta validare, cineva ar putea trimite "   " ca motiv.
}

--- 7.4 auth/dto/register.dto.ts ---

  @MinLength(6) password: string;
  → Parola de cel putin 6 caractere. Validata INAINTE de a ajunge in service.

================================================================================
  8. PURCHASE ORDERS — LOGICA DE BUSINESS
================================================================================

--- 8.1 purchase-orders.service.ts ---

=== create(dto, user) ===
  1. REGULA BUDGET: Daca amount > 2000, PO-ul e PERMANENT respins imediat.
     Se salveaza cu status PERMANENTLY_REJECTED si se creeaza doua intrari
     in history: SUBMITTED si HARD_REJECTED cu mesajul "too expensive, budget exceeded".
     Aceasta previne incarecarea inutila a workflow-ului cu comenzi imposibile.

  2. REGULA MANAGER SKIP: Daca userul e Manager SAU amount < 100,
     etapa de Manager Approval e sarita.
     - Manager skip: un manager nu isi aproba propriile comenzi.
     - Sub 100€ skip: comenzile mici nu necesita aprobare de manager.
     Statusul initial devine: PENDING_IT (daca IT_EQUIPMENT) sau PENDING_FINANCE.

  3. In caz normal: statusul initial e PENDING_MANAGER.
  4. Se salveaza un event SUBMITTED in history.

=== findAll(user) ===
  Returneaza PO-urile vizibile pentru user-ul curent, filtrate dupa rol:
  - REQUESTER: doar propriile PO-uri (WHERE createdById = user.id)
  - MANAGER:   PO-uri la etapa PENDING_MANAGER
  - IT:        PO-uri la etapa PENDING_IT
  - FINANCE:   PO-uri la PENDING_FINANCE / INVOICED / PERMANENTLY_REJECTED
               SAU create de el insusi (OR createdById = user.id)
               → Permite Finance sa-si vada propriile comenzi indiferent de etapa.
  - ADMIN:     toate (no filter)

=== findOne(id, user) ===
  Gaseste un singur PO vizibil pentru user.
  PROBLEMA SPECIALA pentru Finance: getWhereClause returneaza un ARRAY
  (conditii OR). Daca am face { id, ...array }, JavaScript ar produce
  { id, 0: {...}, 1: {...} } — gresit. De aceea:

  const where = Array.isArray(clause)
    ? clause.map(c => ({ ...c, id }))   → adauga id la fiecare conditie OR
    : { ...clause, id };                → cazul simplu (alte roluri)

=== update(id, dto, user) ===
  Permite editarea unui PO doar daca:
  - Statusul e NEEDS_REWORK (a fost respins si returnat pentru revizuire)
  - User-ul e creatorul PO-ului
  Aplica aceleasi reguli ca la create: budget check >2000, skip manager.
  Tranzitia e inregistrata ca REWORKED in history, repornind workflow-ul.

=== approve(id, user) ===
  Tranzitia de status in functie de etapa curenta:
  PENDING_MANAGER → PENDING_IT (daca IT_EQUIPMENT) sau PENDING_FINANCE
  PENDING_IT → PENDING_FINANCE
  PENDING_FINANCE → INVOICED
  Validarea se face in validateApprover().

=== reject(id, dto, user) ===
  Respingere "soft" — statusul devine NEEDS_REWORK.
  Creatorul poate edita si resubmite PO-ul.
  Necesita un comentariu obligatoriu.

=== hardReject(id, dto, user) ===
  Disponibil DOAR pentru Finance.
  Statusul devine PERMANENTLY_REJECTED — nu mai poate fi resubmis.
  Folosit cand bugetul lunar e depasit.
  Finance nu poate face hard-reject pe propriul PO (self-rejection prevention).

=== validateApprover(po, user) ===
  Verifica doua lucruri:
  1. Rolul user-ului corespunde etapei PO-ului:
     PENDING_MANAGER → MANAGER, PENDING_IT → IT, PENDING_FINANCE → FINANCE
  2. SELF-APPROVAL PREVENTION pentru IT si Finance:
     Daca user-ul e creatorul PO-ului SI PO-ul e la etapa IT sau Finance,
     aruncam ForbiddenException. Un angajat nu poate aproba propria comanda.
     (Manager e exclus din aceasta regula pentru ca manager-ii isi creeaza
      PO-uri care sar direct peste etapa lor — nu pot ajunge sa-si aprobe.)

=== getWhereClause(user) ===
  Returneaza conditia WHERE TypeORM filtrata dupa rol.
  Pentru Finance returneaza un ARRAY de conditii = SQL OR:
    (status IN ('PENDING_FINANCE','INVOICED','PERMANENTLY_REJECTED'))
    OR (createdById = 'user-id')

=== getMonthlySpendings() ===
  Query cu QueryBuilder (not find()) pentru agregari:
  Calculeaza SUM(amount) per requester pentru luna curenta,
  excluzand NEEDS_REWORK si PERMANENTLY_REJECTED (comenzi inactive).
  Returneaza lista cu { requesterId, name, email, total } pentru dashboard Finance.

=== getMyApprovals(user) ===
  Returneaza din po_history toate actiunile de tip APPROVED, REJECTED,
  HARD_REJECTED efectuate de user-ul curent, cu PO-ul si creatorul acestuia
  inclusi (relations nested), sortate DESC (cele mai recente primele).
  Baza pentru pagina "Approval History".

=== getHistory(id) ===
  Returneaza toate evenimentele unui PO in ordine cronologica (ASC).
  Fiecare eveniment include: actiunea, tranzitia de status, comentariul
  si utilizatorul care a efectuat actiunea. Afisata ca timeline in UI.

--- 8.2 purchase-orders.controller.ts ---

Toate rutele sunt protejate cu @UseGuards(JwtAuthGuard) aplicat pe intregul
controller. Fara token valid = 401 automat pe orice ruta.

@Get('my-approvals') — IMPORTANT: definit INAINTEA @Get(':id')
  Daca ar fi dupa, NestJS ar interpreta "my-approvals" ca un :id si ar
  incerca sa caute un PO cu id "my-approvals". Ordinea conteaza in NestJS.

@Post('monthly-spending') si @Post(':id/hard-reject'):
  Folosesc POST (nu GET) chiar daca nu creeaza resurse noi.
  monthly-spending nu are parametri in URL, iar hard-reject are body.
  Conventia stricta REST ar folosi GET, dar POST evita cachingul nedorit.

================================================================================
  10. SECURITATE — REZUMAT
================================================================================

1. PAROLE:
   - Stocate ca hash bcrypt cu salt rounds = 10 (nu plaintext, niciodata)
   - @Exclude() + ClassSerializerInterceptor = hash-ul nu apare in niciun
     raspuns API, nici in relatii nested (createdBy, performedBy)

2. JWT:
   - Secret stocat in .env (nu in cod)
   - Expira in 24 ore
   - Verificat la fiecare cerere de JwtAuthGuard + JwtStrategy
   - Payload minimal: { sub, email, role } — nu stocam date sensibile in token

3. AUTORIZARE:
   - JwtAuthGuard: toate rutele (autentificare)
   - RolesGuard + @Roles: rute specifice (autorizare pe rol)
   - validateApprover(): autorizare la nivel de business logic
     (rolul corespunde etapei PO-ului)
   - Self-approval prevention: IT si Finance nu pot aproba propriile PO-uri

4. VALIDARE INPUT:
   - ValidationPipe global cu whitelist: true (elimina campuri necunoscute)
   - @Transform + trim (spatii goale)
   - @IsNotEmpty() (stringuri nevide dupa trim)
   - @MaxLength() (previne payload-uri uriase / DoS)
   - @IsNumber({ maxDecimalPlaces: 2 }) (evita floating point abuse)
   - @IsEnum() (accepta doar valori cunoscute pentru categorii si statusuri)

5. CORS:
   - Configurat explicit pentru origin-ul frontend-ului
   - Browserele blocheaza cererile de la alt origin fara CORS

6. .env:
   - Credentialele DB si JWT_SECRET nu sunt in codul sursa
   - ConfigService le injecteaza la runtime

================================================================================

1. Requester se autentifica → primeste JWT
2. Requester creeaza PO (title, amount, category)
   → ValidationPipe valideaza DTO
   → Daca amount > 2000: PERMANENTLY_REJECTED automat
   → Daca amount < 100 sau creator e Manager: skip Manager stage
   → Altfel: status = PENDING_MANAGER, event SUBMITTED in history
3. Manager vede PO-ul in lista sa → il aproba
   → validateApprover: verifica rol si self-approval
   → Daca IT_EQUIPMENT: status = PENDING_IT
   → Altfel: status = PENDING_FINANCE
   → Event APPROVED in history
4. (Optional) IT vede PO-ul → il aproba
   → status = PENDING_FINANCE, event APPROVED
5. Finance vede PO-ul → il aproba
   → status = INVOICED, event APPROVED
6. Finance marcheaza ca Invoiced (buton separat)
   → Confirmare finala in sistem

La orice etapa, aprobatorul poate:
- REJECT (soft): status = NEEDS_REWORK, Requesterul poate edita si resubmite
- HARD REJECT (Finance only): status = PERMANENTLY_REJECTED, proces incheiat
